## 1. Обзор <a name="overview"></a>

`ActivityEvaluator` хранит для каждой сессии **activity score** — числовую оценку
остаточной уверенности в том, что разработчик всё ещё работает. Score растёт при git-активности
(diff dynamics, коммиты) и линейно затухает каждый poll-тик.

Когда score достигает 0 → авто-пауза. Когда появляется активность на поставленной на паузу сессии → авто-возобновление.

Ключевые цели проектирования:
- **Предсказуемая stamina**: каждый прирост мал и привязан к наблюдаемой работе —
  одно нажатие клавиши покупает фиксированный небольшой запас, шкалу наполняют
  только устойчивая частота и объём, а достичь 100% намеренно трудно
- **Никакого шума пауз**: любое касание гарантирует запас в несколько минут
  (порог касания, touch floor), никогда не «1 строка = 1 минута»
- **Детекция паузы по смене поведения**: затухание асимметрично — чем плотнее
  недавняя работа, тем быстрее буфер остывает после резкой остановки
  (полная шкала Normal угасает за ~30 мин, а не за 45), но ускоренное затухание
  никогда не пробивает порог касания — минуты порога гарантированы при любой EMA
- **Кросс-репозиторная осведомлённость**: в один момент времени внимание может удерживать
  только один репозиторий; лидерство следует за коротким окном внимания
  и не зависит от наполненности шкал
- **Независимость от единиц времени**: алгоритм работает корректно при любом значении `diffPollSeconds`

## 2. Константы и независимость от длительности тика <a name="constants"></a>

**Все константы алгоритма выражены в человекочитаемых единицах времени (минуты, секунды).**
Тиковые значения вычисляются при создании `ActivityEvaluator`.

### Исходные константы (во временных единицах)

**Чувствительность** (sensitivity) репозитория задаёт единственную ручку — максимальный
таймаут / потолок stamina (`SENSITIVITY_TIMEOUTS`). Порог касания (touch floor)
*выводится* из него (`× STAMINA_FLOOR_RATIO = 1/4`), отдельной min-константы нет:

| Чувствительность | max (потолок) | производный порог касания |
|-------------|---------------|---------------------|
| `low` | 15 мин | 3.75 мин |
| `normal` (по умолчанию) | 45 мин | 11.25 мин |
| `patient` | 90 мин | 22.5 мин |
| `always_on` | 45 мин (idle-таймаут игнорируется) | 11.25 мин |

| Константа | Значение | Единица | Описание |
|-----------|----------|---------|----------|
| `STAMINA_FLOOR_RATIO` | 1/4 | — | Порог касания как доля от потолка |
| `EMA_WINDOW_MINUTES` | 10 | мин | Окно сглаживания EMA частоты |
| `ATTENTION_WINDOW_MINUTES` | 2 | мин | Окно EMA внимания (кросс-репозиторное лидерство) |
| `COMMIT_BONUS_SECONDS` | 240 | сек | Дополнительные очки от коммита (в эквиваленте таймаута) |
| `FREQUENCY_GAIN_MAX` | 2 | — | Прирост за частоту на активный тик при EMA = 1 |
| `STAMINA_LINES_PER_MINUTE` | 8 | строки | Churn, дающий +1 очко/мин (→ 4 строки на 30с-тик) |
| `VOLUME_GAIN_MAX` | 8 | — | Потолок прироста за объём на тик |
| `DECAY_BOOST` | 2 | — | Дополнительное затухание за тик простоя × EMA (асимметричное угасание, порог не пробивается) |
| `IN_PLACE_CHURN_LINES` | 8 | строки | Строки-эквиваленты за файл, переписанный «на месте» (плоские числа diff, изменившийся хеш содержимого) |
| `CHURN_MAX_FILES` | 100 | файлы | Лимит churn-сканера: максимум файлов на чтение/хеширование за тик |
| `CHURN_MAX_FILE_BYTES` | 2 МБ | байты | Лимит churn-сканера: слишком большие файлы пропускаются (бинарные тоже) |

### Производные константы (в тиках)

Все вычисляются из `diffPollSeconds` (значение из конфига, по умолчанию 30):

```
tickSeconds = config.session.diffPollSeconds

MAX_TICKS           = sensitivity.max * 60 / tickSeconds
FLOOR_TICKS         = MAX_TICKS * STAMINA_FLOOR_RATIO
EMA_ALPHA           = 1 / (EMA_WINDOW_MINUTES * 60 / tickSeconds)
ATTENTION_ALPHA     = 1 / (ATTENTION_WINDOW_MINUTES * 60 / tickSeconds)
COMMIT_BONUS        = COMMIT_BONUS_SECONDS / tickSeconds
LINES_PER_GAIN_TICK = STAMINA_LINES_PER_MINUTE * tickSeconds / 60   // 4 at 30s
```

### Таблица производных значений для разных `diffPollSeconds` (чувствительность normal)

| Конфиг | MAX_TICKS | FLOOR_TICKS | EMA_ALPHA | ATTENTION_ALPHA | COMMIT_BONUS |
|--------|-----------|-------------|-----------|-----------------|--------------|
| 15с    | 180       | 45          | ~0.025    | 0.125           | 16           |
| 30с    | 90        | 22.5        | ~0.05     | 0.25            | 8            |
| 45с    | 60        | 15          | ~0.075    | 0.375           | ~5           |
| 60с    | 45        | 11.25       | ~0.10     | 0.5             | 4            |

Диапазон таймаута [11.25, 45] минут сохраняется при любой длительности тика.

## 3. Модель интенсивности на базе EMA <a name="ema"></a>

**Экспоненциальное скользящее среднее (EMA)** отслеживает насколько интенсивно работает разработчик.

### Формула

```
Каждый тик:
  hasActivity = hasDynamics || hasCommit
  activityLevel = hasActivity ? 1.0 : 0.0

  intensityEMA = EMA_ALPHA × activityLevel + (1 - EMA_ALPHA) × intensityEMA
```

EMA использует **бинарный вход** (есть активность или нет). Магнитуда дельты
применяется отдельно к объёмной компоненте score (см. §5), а не к EMA. Это сохраняет
чистую семантику EMA: она отвечает на вопрос «как часто разработчик производит
изменения?», а не «насколько большие эти изменения?».

### Поведение EMA

EMA варьируется от 0.0 (нет недавней активности) до ~1.0 (непрерывная активность).
При `EMA_ALPHA ≈ 0.05` (10-минутное окно, тики 30с):

| Паттерн работы | Установившееся EMA | Формула расчёта |
|---------------|-------------------|----------------|
| Каждый тик (интенсивная) | ~1.00 | Сходится к 1.0 |
| Каждый 3-й тик | ~0.33 | α / (1 - (1-α)^3) при α=0.05 |
| Каждый 5-й тик | ~0.22 | α / (1 - (1-α)^5) |
| Каждый 10-й тик (5 мин промежуток) | ~0.12 | α / (1 - (1-α)^10) |
| Каждый 30-й тик (15 мин промежуток) | ~0.05 | α / (1 - (1-α)^30) |

### Затухание EMA во время простоя

При 10-минутном окне EMA сохраняет память через короткие перерывы:

| Время простоя | EMA (была 0.65) | Смысл |
|--------------|----------------|-------|
| 0 мин | 0.65 | Только остановился |
| 2.5 мин | 0.53 | Ещё помнит интенсивность |
| 5 мин | 0.39 | Умеренная память |
| 10 мин | 0.23 | Начинает забывать |
| 15 мин | 0.14 | Почти забыл |
| 30 мин | 0.03 | Практически забыл |
| 45 мин | ~0 | Чистый лист |

### EMA во время паузы

- **Ручная пауза**: полная заморозка. Evaluator не получает сессию → EMA, score
  и всё состояние остаются ровно такими, какими были. При resume обработка
  продолжается с замороженного состояния. Замороженный score естественно
  выполняет роль grace period.
- **Авто-пауза** (IdleTimeout/Superseded): evaluator продолжает получать сессию.
  Score обновляется нормально (может накапливаться при активности).
  EMA продолжает обновляться каждый тик.

## 4. Модель score «Stamina» <a name="adaptive-max"></a>

Score — это **буфер выносливости (stamina)**: число тиков, оставшихся до авто-паузы,
и одновременно значение, стоящее за шкалой Stamina (`normalizedScore = score / MAX_TICKS`).
Потолок зафиксирован на `MAX_TICKS`; варьируется лишь скорость наполнения буфера —
небольшие явные приросты, привязанные к наблюдаемой работе.

### Обновление score за один тик

```
if (hasActivity):                          // dynamics or commit
  1. score = max(score, MAX_TICKS × STAMINA_FLOOR_RATIO)              // touch floor
  2. score += min(1, intensityEMA) × FREQUENCY_GAIN_MAX               // frequency gain
  3. score += min(VOLUME_GAIN_MAX, deltaMagnitude / LINES_PER_GAIN_TICK)  // volume gain
  4. if (hasCommit): score += COMMIT_BONUS
  5. score = min(score, MAX_TICKS)                                    // fixed ceiling

6. floor = MAX_TICKS × STAMINA_FLOOR_RATIO
   if (!hasActivity AND score > floor):
     score = max(floor, score - (1 + DECAY_BOOST × min(1, intensityEMA)))
     // асимметричное угасание — буст никогда не пробивает порог, см. ниже
   else:
     score = max(0, score - 1)             // активный тик, либо на/ниже порога
7. if (score == 0): → AutoPause decision
```

### Порог касания (touch floor)

Любой активный тик поднимает score минимум до `MAX_TICKS × STAMINA_FLOOR_RATIO`
(Normal: 45 / 4 = **11.25 мин**, 25% шкалы). Сразу две гарантии:

- одно нажатие клавиши не может подбросить шкалу до половины (старый алгоритм: один тик = ~52%)
- одно нажатие клавиши всё равно покупает запас в несколько минут — никогда не
  «1 строка = 1 минута до паузы», поэтому лёгкая работа не создаёт шума пауз

### Прирост за частоту (frequency gain)

`min(1, EMA) × FREQUENCY_GAIN_MAX` (макс. +2/тик) — вознаграждает устойчивый поток
обновлений. При затухании −1/тик одна лишь частота обгоняет затухание, как только
EMA > 0.5, на что нужно ~7 минут активности тик за тиком. Спорадические правки
(EMA ≪ 0.5) на одной частоте никогда не растут — они держатся у порога.

### Прирост за объём (volume gain)

`min(VOLUME_GAIN_MAX, lines / LINES_PER_GAIN_TICK)` — линеен по числу изменённых
строк за тик, с ограничением сверху:

| Изменено строк за тик | Прирост за объём | Чистый эффект против затухания (−1) |
|----------------------|------------|--------------------|
| 1 | +0.25 | отрицательный |
| 4 | +1.0 | ноль (breakeven) |
| 8 | +2.0 | +1 |
| 12 | +3.0 | +2 |
| 24 | +6.0 | +5 |
| 32+ | +8.0 (cap) | +7 |

Ограничение означает, что массовая вставка сгенерированного файла стоит максимум +8 —
наполнение шкалы всегда требует *устойчивой* активности и никогда — одного события.

### Асимметричное угасание (детекция паузы)

Наполнение — медленное и заработанное; опустошение — это **детекция смены
поведения**. На тиках простоя **выше порога касания** затухание равно
`1 + DECAY_BOOST × EMA`: чем плотнее была недавняя активность, тем быстрее
буфер остывает после остановки. Резкая тишина после кодинга тик за тиком —
самый сильный сигнал паузы из возможных, причём EMA сама остывает во время
тишины, поэтому затухание возвращается к 1/тик за ~10 минут.

Буст **экранирован порогом**: за один сегмент простоя он может слить score
до порога, но никогда сквозь него, а на/ниже порога затухание — всегда обычный
1/тик. Поэтому гарантия «любое касание покупает минуты порога (Normal: 11.25 мин)
до паузы» выполняется при *любой* EMA. Без этого экрана горячая EMA (≈1)
сливала бы шкалу на уровне порога куда быстрее, порождая шквал пауз, стоило
интенсивному потоку на минуту затихнуть.

| Состояние в момент остановки (Normal) | Время до авто-паузы |
|---------------------------------------|---------------------|
| Полная шкала, EMA ≈ 1 (интенсивная серия) | ~30 мин (быстрый сегмент до порога ~18 мин + порожный сегмент ~11 мин) |
| Половина шкалы, EMA ≈ 0.5 (умеренная работа) | ~18 мин |
| Шкала на уровне порога, EMA ≈ 1 (горячий поток только начался) | ~11 мин (экран порога) |
| Порог после одного касания, EMA ≈ 0 | ~11 мин |
| Patient, полная шкала, EMA ≈ 1 | ~71 мин (долгий уход ловится) |

Поскольку затухание больше не константа, обратный отсчёт до авто-паузы
сообщается как `etaTicks` (симуляция угасания), а не как сырой score.

### Время наполнения шкалы (чувствительность Normal, тики 30с)

| Паттерн работы | Поведение шкалы |
|--------------|--------------|
| Одно касание | прыжок до 25%, затухание, пауза через ~11 мин |
| Спорадические правки в 1 строку раз в несколько минут | держится у ~25%, не растёт |
| Обновление каждый тик, 1–3 строки | насыщение за ~30–40 мин непрерывной работы |
| Каждый тик, ~10 строк | насыщение за ~13 мин |
| Каждый тик, 32+ строк-эквивалентов churn (cap) — набранных, переписанных агентом или закоммиченных | насыщение за ~5 мин — всё равно не мгновенно |

## 5. Объёмная компонента <a name="magnitude"></a>

Магнитуда дельты (строки-эквиваленты churn) питает **прирост за объём (volume gain)**, а не EMA.
EMA отслеживает частоту активности (бинарно: есть или нет).
Объём отслеживает интенсивность каждого события активности (сколько было churn).

### Источник churn: per-file, три слоя

`deltaMagnitude` — это per-file оценка **churn** в строках-эквивалентах,
никогда не разность просуммированных итогов:

1. **Per-file churn по diff** — `|Δadded| + |Δremoved|` по каждому файлу
   поверх *evidence diff* (закоммиченное + staged + рабочее дерево против
   свежего merge-base; при отсутствии базы — откат к обычному diff рабочего
   дерева). Поскольку diff заякорен на merge-base, куски, закоммиченные
   сразу же, остаются видимыми, а переносы между файлами не могут
   взаимно сократиться. Файл, *входящий* в churn-карту, считается целиком;
   файл, *покидающий* её, считается по последнему известному размеру
   (revert / переякоривание).
2. **Untracked-файлы** — совершенно новые файлы невидимы любому git diff,
   поэтому они перечисляются через `git ls-files --others --exclude-standard`
   (добавлено в общий git-батч) и читаются с диска: количество их строк —
   это их «added». Агент, выгрузивший новый файл на 300 строк, регистрирует
   300 строк-эквивалентов немедленно. Бинарные и слишком большие
   (> `CHURN_MAX_FILE_BYTES` = 2 МБ) файлы пропускаются; весь скан ограничен
   `CHURN_MAX_FILES` = 100 файлами за тик.
3. **Детекция переписывания «на месте»** — файл, чьи числа diff между тиками
   плоские, но хеш содержимого изменился (строки и так отличались от базы,
   поэтому numstat не видит переписывание), даёт `IN_PLACE_CHURN_LINES` = 8
   строк-эквивалентов. Хеши считаются только для «плоских» файлов, так что
   накладные расходы малы; детекция запаздывает на один тик при первом
   «уплощении» файла.

Формула прироста в evaluator не изменилась:
`min(VOLUME_GAIN_MAX, deltaMagnitude / LINES_PER_GAIN_TICK)` — максимум +8
за 30с-тик, достигается на 32 строках-эквивалентах churn.

### Почему per-file churn, а не нетто-итоги?

Предыдущим источником была `|Δadded| + |Δremoved|` от *просуммированного
numstat рабочего дерева* между тиками. Неттинг итогов был слеп к:
(а) переписыванию уже изменённых строк (числа numstat не двигаются),
(б) межфайловым переносам (+20 одного файла гасит −20 другого),
(в) untracked-файлам (никакого diff вообще),
(г) кускам, закоммиченным сразу (они покидают diff рабочего дерева).
На практике агент, переписывающий крупные куски и коммитящий каждый шаг,
регистрировал ~0 объёма — шкала висела у порога во время плотной работы
на машинной скорости.

### Проектирование: разделение ответственности

| Метрика | Вклад | На какой вопрос отвечает |
|--------|-------------|---------------------|
| EMA (бинарная) | прирост за частоту (макс. +2/тик) | «Как часто разработчик производит изменения?» |
| Магнитуда | прирост за объём (макс. +8/тик) | «Насколько большие изменения, когда они происходят?» |

Обе компоненты аддитивно питают один и тот же буфер stamina, поэтому шкала отражает
*частоту × объём* — ровно ту интуицию «насколько интенсивно идёт работа в этом репозитории».

### Почему линейно с ограничением (а не логарифм)?

Предыдущая модель использовала логарифмический бонус (`log2(1+n)/7`, ограничен ×1.5)
поверх огромной базовой добавки за тик (50% потолка). Результат: 1 строка и 1000 строк
были почти неразличимы, а любые два активных тика насыщали шкалу. Линейный прирост
за объём с ограничением делает разницу между 2 строками (+0.5) и 12 строками (+3)
видимой, а само ограничение (32+ строк) не даёт массовым вставкам обмануть шкалу.

## 6. Кросс-репозиторное лидерство <a name="leadership"></a>

### Принцип

**В один момент времени только одна сессия может быть «лидером» (активно трекать время).**
Лидер определяется выделенной **EMA внимания (attention EMA)** (2-минутное окно,
бинарный вход — как у EMA частоты) с гистерезисом перехвата — а *не* по stamina score.
Stamina по замыслу медленная и труднонаполняемая, поэтому сравнение по stamina
задерживало бы передачу репозитория на 5–10 минут; внимание следует за разработчиком
в пределах ~2 минут вне зависимости от наполненности шкал.

### Механизм

```
На каждый вызов processAllTicks():
  1. Обновить score и attention EMA для ВСЕХ сессий (кроме ручных пауз)
  2. Кандидаты = сессии со score > 0
  3. Текущий лидер сохраняет лидерство, пока внимание претендента не превысит
     его больше чем на ATTENTION_ALPHA (= вклад одного изолированного касания)
  4. Без защищающегося лидера: побеждает наивысшее внимание
     (normalizedScore как tiebreak)
  5. Все остальные сессии со score > 0: на паузу (PauseSource.Superseded)
  6. Сессии со score == 0: на паузу (PauseSource.IdleTimeout)

Важно: сессии-нелидеры НЕ замораживаются в evaluator.
  Их score продолжает обновляться (накопление при активности, затухание при простое).
  Это позволяет им конкурировать и обогнать текущего лидера.
```

### Почему гистерезис?

Один активный тик поднимает внимание ровно на `ATTENTION_ALPHA` (0.25 при тиках 30с).
Запас перехвата равен той же величине, поэтому **одно случайное сохранение по построению
никогда не может украсть лидерство** — даже если текущий лидер какое-то время простаивал.
Настоящее переключение (старое репо простаивает, новое активно тик за тиком) пересекает
запас за ~4–5 тиков (~2 мин при опросе 30с).

Когда оба репо простаивают, их EMA внимания затухают пропорционально, поэтому их
порядок — и лидер — остаётся стабильным (никакого дребезга).

### Несколько репо с активностью (один тик)

Если у двух репо есть dynamics в одном и том же тике, обе EMA внимания растут
одинаково, и гистерезис сохраняет текущего лидера (редкий граничный случай —
обычно это и так фронтенд/бэкенд одной задачи).

### PauseSource

```typescript
enum PauseSource {
  Manual = 'manual',                     // workday pause
  IdleTimeout = 'idle_timeout',          // score достиг 0
  Superseded = 'superseded',             // другая сессия имеет выше нормализованный score
  TeamsAway = 'teams_away',             // Фаза 3
}
```

### Ключевое отличие от предыдущих версий

| | AttentionSteal (v0) | Normalized score (v1) | Attention EMA (v2, текущая) |
|---|---|---|---|
| Обнаружение | счётчик consecutiveActiveTicks | пересечение stamina score | выделенная 2-минутная EMA |
| Скорость передачи | 2 мин (жёсткий порог) | быстрая лишь потому, что один тик давал 50% шкалы | ~2 мин, независимо от наполненности шкалы |
| Иммунитет к случайному касанию | на основе порога | norm < norm лидера | невозможно по построению (запас = одно касание) |
| Стабильность при простое | — | затухает с более высокого значения | пропорциональное затухание, порядок сохраняется |

## 7. Жизненный цикл score и машина состояний <a name="score-lifecycle"></a>

### Машина состояний

```
                 стал лидером (score > 0)
  Pending ───────────────────────────────► Active
    │                                        │  ▲
    │                                        │  │ вернул лидерство
    │                                        │  │ (закрытие паузы)
    │                                        ▼  │
    │                                    Active(paused)
    │                                    Superseded / IdleTimeout
    │                                        │
    │  checkout / day boundary / stop         │
    └───────────────► Closed ◄───────────────┘
```

Состояния:
- **Pending**: сессия существует, evaluator считает score, время НЕ трекается.
  `startedAt` ещё не установлен. Промоция требует score > 0 И лидерства.
- **Active**: сессия была или является лидером, время трекается.
  `startedAt` устанавливается в момент промоции Pending → Active.
  Может быть на паузе (Superseded/IdleTimeout), но остаётся Active.
- **Closed**: сессия завершена. `closedBy` записывает причину.

Важно: **Active никогда не возвращается в Pending.** Потеря лидерства = пауза, не понижение.

### Открытие сессии

```
score = 0
intensityEMA = 0
state = Pending
startedAt = null (устанавливается при промоции в Active)
```

Сессия начинается в состоянии `Pending`. Evaluator получает её и считает score.
Трекинг времени не начинается, пока сессия не станет лидером.

### Pending → Active (промоция)

```
Происходит когда:
  1. score > 0 (была хотя бы одна активность)
  2. сессия — лидер (attention EMA, см. §6)

  startedAt = now
  state = Active
  Трекинг времени начинается
```

**Оба условия обязательны.** Сессия с score = 0 не может стать лидером,
даже если она единственная. Это защищает от промоции «пустых» сессий.

Для одного репо: первый dynamics → score > 0 → единственная сессия → лидер → Active.
Для нескольких репо: сессия может оставаться Pending пока другая сессия лидирует,
накапливая внимание до момента перехвата.

### Нормальная работа (Active сессия)

```
Каждый тик:
  1. Обновить EMA частоты и attention EMA (бинарно: активность=1, простой=0)
  2. При активности: порог касания, прирост за частоту, прирост за объём,
     бонус за коммит, ограничение MAX_TICKS
  3. Применить затухание (1 на активных тиках; 1 + DECAY_BOOST × EMA на тиках
     простоя выше порога — никогда сквозь порог; 1/тик на/ниже порога)
  4. Выбрать лидера (attention EMA с гистерезисом перехвата, §6)
  5. Если по-прежнему лидер → продолжить трекинг времени
  6. Если score == 0 → пауза IdleTimeout
  7. Если претендент перехватил лидерство → пауза Superseded
```

### Авто-пауза: IdleTimeout (score == 0)

```
При IdleTimeout (Active сессия, score достиг 0):
  Запись Pause: PauseSource.IdleTimeout
  Evaluator продолжает обрабатывать (score обновляется, EMA затухает)
  Возобновление: когда приходит dynamics/commit → score > 0 → может снова стать лидером
```

### Idle auto-close + хвостовой трим (честный конец сессии)

```
Открытая IdleTimeout-пауза старше config session.idleCloseHours
(дефолт 3, 0 = выключено) закрывает сессию: ClosedBy.IdleTimeout.
Проверка — первым шагом каждого тика демона: после сна ПК устаревшая
сессия закрывается ДО того, как активность пробуждения родит новую.

Каждый путь закрытия (checkout, rollover, stop, crash recovery, idle
auto-close) тримит хвостовую цепочку пауз: конец сессии = начало цепочки
(последняя реальная активность), цепочка удаляется из записи. Смежные
паузы (транзит Superseded → IdleTimeout) тримятся как одна цепочка.
Закрытая хвостовая пауза (после неё была активность) не тримится.
Effective-время не меняется — тримленные паузы и так вычитались.

Manual-пауза не авто-закрывается (замороженная сессия ждёт пользователя),
но её хвост при закрытии тримится как любой другой.
Новая активность после авто-закрытия рождает новую сессию (lazy sessions).
```

### Гэп наблюдения (сон / гибернация ПК)

```
Пока машина спит, таймеры не тикают: evaluator не затухает, lastSeenAt не
двигается — первый тик после пробуждения засчитал бы весь гэп как работу.
Демон хранит lastAliveAt (обновляется poll-тиком и 60s boundary-таймером)
и на обоих проверяет:

  гэп = now − lastAliveAt > max(3 × diffPollSeconds, 120s)

При гэпе:
  1. Каждая открытая НЕзапаузенная сессия получает ретроактивную
     IdleTimeout-паузу от своего pre-gap lastSeenAt — последнего момента,
     когда работа реально наблюдалась. Уже запаузенные сессии не трогаются
     (их пауза естественно накрывает гэп); manual-паузы неприкосновенны.
  2. Кандидаты сбрасываются, состояние evaluator очищается — score это
     предсонные остатки; реальная активность заработает всё заново (touch floor).
  3. Сразу же выполняется idle auto-close: гэп ≥ idleCloseHours → сессия
     закрывается немедленно с честным концом (последняя предсонная активность).

Итог: короткое закрытие крышки (< idleCloseHours) — пауза внутри той же
сессии, авто-resume при активности; ночной сон закрывает сессию предсонным
концом, утренняя активность рождает новую. Гэп-чек выполняется и перед
rollover — сон через границу дня никогда не закрывает сессии временем
пробуждения. Прыжок часов назад (NTP) лишь переякоривает lastAliveAt.
```

### Авто-пауза: Superseded (потеря лидерства)

```
При Superseded (Active сессия, другая сессия перехватила лидерство по вниманию):
  Запись Pause: PauseSource.Superseded
  Evaluator продолжает обрабатывать (score и EMA обновляются)
  Score может быть > 0 — сессия может конкурировать и вернуть лидерство
  Возобновление: когда её внимание снова пересечёт запас перехвата → закрытие паузы
```

**Ключевое: Superseded-сессии НЕ замораживаются.** Их состояние в evaluator
продолжает обновляться. Они могут вернуть лидерство, снова привлекая
внимание разработчика.

### Авто-возобновление

```
Когда Active-сессия на паузе снова становится лидером:
  Закрываем запись Pause (устанавливаем таймстамп `to`)
  Сессия возобновляет трекинг времени

Это происходит естественно через сравнение внимания.
Также: dynamics/commit на сессии с ручной паузой → авто-возобновление (случай «забыл resume»).
```

### Ручная пауза

```
workday pause [repo]:
  Применяется только к Active-сессиям (Pending-сессии и так не трекают время).
  SessionTracker перестаёт отправлять эту сессию в ActivityEvaluator.
  Состояние в evaluator (score, EMA) остаётся замороженным.
  Авто-возобновление ВОЗМОЖНО при git-активности (dynamics или commit).
  SessionTracker обрабатывает это: обнаруживает активность → закрывает паузу → размораживает.
```

### Ручное возобновление (workday resume)

```
workday resume:
  Закрывает ВСЕ открытые паузы (manual, idle_timeout, superseded)
  SessionTracker возобновляет отправку сессий в ActivityEvaluator
  Evaluator продолжает с замороженного состояния (score, EMA сохранены)
  Замороженный score выступает естественным grace period:
    сколько stamina оставалось на момент паузы — столько бюджета и есть,
    чтобы снова начать кодить (замороженная EMA тоже возобновляется,
    так что скорость угасания сохраняется)
  Никакой специальной логики resume в evaluator не нужно
```

### Отключение авто-паузы (workday autopause off)

```
workday autopause off [repo]:
  Score продолжает обновляться (для отображения в статусе), но:
    - IdleTimeout подавляется (score=0 не вызывает паузу)
    - Смена лидерства по-прежнему работает (Superseded действует)
  Сессия остаётся активной как лидер бессрочно до:
    - workday autopause on [repo]
    - workday pause [repo]
    - Другая сессия обгоняет (Superseded)
    - Граница дня (day boundary)
    - Остановка демона
```

### Закрытие сессии

```
evaluator.removeSession(sessionId):
  Удаляем всё in-memory состояние (score, EMA)
```

## 8. Модель «стакан воды» <a name="glass-of-water"></a>

Внимание разработчика — конечный ресурс, как вода в стакане.

### Метафора

Стаканы stamina наполняются и опустошаются независимо; **внимание** (в чей стакан
льют прямо сейчас) решает, кто трекает время:

```
Репо A (Active):   [████████░░]  attention≈1.0   «лидер, трекает время»
Репо B (Pending):  [░░░░░░░░░░]  attention=0     «копит, не трекает»

Разработчик переключается на B (A простаивает, B активно каждый тик):

Тик 1:  B att=0.25 vs A att=0.75+0.25 запас → A всё ещё лидер
Тик 2:  B att=0.44 vs A att=0.56+0.25       → A всё ещё лидер
Тик 4:  B att=0.68 vs A att=0.32+0.25=0.57  → B перехватывает!
         B: Pending → Active (startedAt = сейчас, трекинг начинается)
         A: Active → пауза (Superseded)

Разработчик возвращается в A: симметрично, A возвращает лидерство за ~4 тика.
```

### Почему не явный перенос?

Мы рассматривали: «репо B получает → репо A теряет (бюджет с нулевой суммой)».

Модель лидерства проще: оба стакана существуют независимо,
а EMA внимания решает, кто трекает время.
Никакого переноса, никакого перераспределения —
естественная конкуренция через активность и затухание.

## 9. CLI-команды <a name="cli-commands"></a>

### workday resume

Закрывает ВСЕ открытые паузы вне зависимости от источника (manual, idle_timeout, superseded).
Если пользователь явно написал «resume» — он знает что делает.

В будущем: интеграция Teams будет вызывать HTTP-endpoint resume для сигнала «пользователь вернулся».

### workday autopause off [repo]

Отключает IdleTimeout для указанного репозитория или для всех репо, если аргумент не указан.
Смена лидерства (Superseded) по-прежнему работает — нельзя быть лидером двух репо одновременно.

Сессия не получает IdleTimeout при score=0. Score продолжает обновляться (виден в `workday status`).

Сбрасывается при:
- `workday autopause on [repo]`
- Граница дня (чистое состояние на новый день)
- Остановка/перезапуск демона

`workday status` должен показывать предупреждение: «⚠ autopause disabled для atlas-frontend (с 14:30)»

### workday pause [repo]

Ручная пауза. Перекрывает авто-паузу. Может быть снята:
- `workday resume` — явное ручное возобновление
- Git-активность (dynamics или commit) — автоматически, на случай «забыл нажать resume»

## 10. Разбор сценариев <a name="scenarios"></a>

Все примеры используют `diffPollSeconds=30` (1 тик = 30 секунд).

### Сценарий A: Интенсивная работа, потом обед

```
Разработчик пишет код с dynamics практически каждый тик в течение 2 часов (10–15 строк/тик).

Фаза 1: Работа
  EMA → ~1.0 в течение ~10 мин (бинарный вход, активность каждый тик)
  Прирост за тик ≈ 2 (частота) + 3–4 (объём) − 1 (затухание) → чистыми +4..5
  Score: от порога в 22.5 тика до потолка в 90 тиков за ~10-13 мин, дальше на потолке
  (Агентная работа ведёт себя так же: per-file churn считает крупные
  переписывания, новые файлы и сразу закоммиченные шаги, поэтому сессия
  Claude Code насыщает шкалу так же быстро, как ручной набор.)

Фаза 2: Начало обеденного перерыва (шкала была полной, EMA ≈ 1)
  Асимметричное угасание: затухание = 1 + 2×EMA ≈ 3/тик вначале,
  ослабевает по мере остывания EMA и останавливается на пороге
  (ниже него — всегда 1/тик)
  Score 90 → порог 22.5 за ~36 тиков, → 0 за ~59 тиков суммарно
  AutoPause (IdleTimeout) через ~30 мин после последней правки —
  резкая остановка после плотной работы остывает быстрее спорадической,
  но мягко — долгое раздумье не путается с перерывом

Фаза 3: Возврат с обеда (через 1 час)
  EMA во время паузы: 1.0 × (1-0.05)^120 ≈ 0.002 (полностью затухла)
  Первый dynamics → AutoResume, score = порог 22.5 (+ небольшие приросты) ≈ запас 11 мин
  Шкала восстанавливается по мере возобновления потока правок
```

### Сценарий B: Лёгкий кодинг (1 строка каждые 15 мин)

```
Разработчик читает код и делает редкие мелкие правки.
Промежуток между dynamics: 30 тиков (15 мин) — длиннее порога в 22.5 тика.

Каждое касание:
  score = порог 22.5 (+ ~0.3 приростов) → затухает до 0 за ~22 тика
  → IdleTimeout через ~11 мин после касания
  → авто-возобновление при следующем касании

При чувствительности Normal такой стиль логирует ~11 мин на касание
с паузами между ними. Так и задумано: 15 минут простоя между
однострочными правками — по большей части не работа. Если для этого репо
они ВСЁ ЖЕ работа (код с большой долей исследования), переключите репо
на Patient: порог = 90/4 = 22.5 мин — тогда каждый промежуток до 22.5 мин
покрыт, и сессия остаётся непрерывной.
```

### Сценарий C: Переключение между репозиториями (лидерство по вниманию)

```
Два репозитория: atlas-frontend (A), appone-backend (B).

12:00  Работаю в A. attention_A ≈ 1.0, шкала на ~60%.
12:05  Переключение на B, начало кодинга (A простаивает).

Тик 1: B att = 0.25 vs A att 0.75 + 0.25 запас → A всё ещё лидер ✓
Тик 2: B att = 0.44 vs A att 0.56 + 0.25       → A всё ещё лидер
Тик 4: B att = 0.68 vs A att 0.32 + 0.25 = 0.57 → B берёт лидерство!
        (~2 мин после переключения)
        B: Pending → Active (startedAt = сейчас)
        A: Pause { source: "superseded" }, score продолжает затухать (не заморожен)

12:30  Возврат в A → симметрично: A возвращает лидерство за ~4 тика,
       пауза A закрыта, B → Superseded → затухает → со временем IdleTimeout.

Результат:
  A в логе: 12:00-12:07 активно, 12:07-12:32 пауза(superseded), 12:32+ активно
  B в логе: startedAt=12:07 (промоция из Pending), активно до 12:32
  Пересечение: 0 сек
```

### Сценарий D: Случайное касание в неактивном репо

```
Разработчик активно работает в repo A (лидер, attention ≈ 1.0).
Случайно сохранил файл в repo B.

Тик 0: dynamics в B (1 строка)
  B: score = порог 22.5 (шкала 25%), attention = 0.25
  A: attention ≈ 1.0 → претенденту нужно > 1.25 — невозможно
  A остаётся лидером; B остаётся Pending

Даже если A простаивал несколько минут, одно касание поднимает внимание
ровно на величину запаса перехвата — превысить запас оно не может никогда.
Случайные сохранения структурно неспособны украсть лидерство.

Больше активности в B нет:
  B score затухает: 15 → 14 → ... → 0 на тике ~15
  B закрывается как Pending при score=0 или при checkout → исключается из отчёта
```

### Сценарий E: Коммит, потом продолжение работы

```
Разработчик кодит (шкала ~50%, score ≈ 45), коммитит, продолжает.

Тик N+1: git add . && git commit
  Diff рабочего дерева: 0/0 (чистое дерево) → итоги дерева прыгают → hasDynamics = TRUE
  Evidence diff (против merge-base) коммитом не меняется →
  per-file churn-магнитуда ≈ 0 (коммит — не новый churn)
  reflog: новый коммит → hasCommit = TRUE

  Score: 45 + 2 (частота) + 0 (объём) + 8 (COMMIT_BONUS) − 1 ≈ 54
  Коммит заметно пополняет шкалу и никогда её не роняет.

Тик N+2 (нового кода пока нет):
  ни churn, ни движения итогов → hasDynamics = FALSE → обычное затухание, score 53
  Запаса достаточно, чтобы обдумать следующий шаг.
```

### Сценарий F: Отключённая авто-пауза (чтение/размышления)

```
Разработчик вернулся с обеда, хочет почитать код какое-то время.

13:00  workday resume → все паузы закрыты
13:00  workday autopause off → авто-пауза отключена для всех сессий
       Статус показывает: «⚠ autopause disabled (с 13:00)»

13:00-14:30  Разработчик читает код, нет git-изменений.
       Score: 0 (нет активности). Но AutoPause подавлена.
       Сессии остаются активными. Время логируется.

14:30  Разработчик начинает кодить → появляются dynamics
       Score: порог + приросты, шкала восстанавливается
       workday autopause on → возвращаем нормальное поведение
```

### Сценарий G: Интервал опроса 60с (независимость от единиц времени)

```
diffPollSeconds = 60, чувствительность Normal.

Производные константы:
  MAX_TICKS = 45 * 60 / 60 = 45 тиков
  FLOOR_TICKS = 45 / 4 = 11.25 тиков (= 11.25 мин, как и при опросе 30с ✓)
  EMA_ALPHA = 1/10 = 0.10
  ATTENTION_ALPHA = 1/2 = 0.5

Касание покупает те же 11.25 минут; потолок — те же 45 минут;
наполнение шкалы требует той же интенсивности в строках-в-минуту
(делитель объёма задан на тик, а тики вдвое длиннее). Все временные
гарантии сохраняются при любой длительности тика.
```

## 11. Граничные случаи <a name="edge-cases"></a>

### Восстановление после краша

При перезапуске демона `ActivityEvaluator` не имеет in-memory состояния.
Все сессии начинают с score=0, EMA=0. Существующие открытые сессии:
- Если следующий poll имеет dynamics → обрабатывается как холодный старт (щедрый таймаут)
- Если нет dynamics → score=0 → AutoPause на первом тике

Это допустимо: краш означает потерю состояния. Быстрая авто-пауза
с последующим авто-возобновлением при активности — самое безопасное поведение.

### Граница дня

Все сессии закрываются через `ClosedBy.DayBoundary`. Состояние evaluator обнуляется.
Новый день начинается полностью с чистого листа.

### Быстрое переключение между репо (пинг-понг)

Разработчик чередует репо A и B каждую минуту (фронтенд + бэкенд одной задачи).
Лидерство следует за вниманием (attention EMA): кто кодит в данный момент, тот лидер.
Паузы Superseded создаются и закрываются при каждом переключении.

Если задача одна (ATL-123 в обоих репо) — пересечения не влияют на итоговый отчёт,
т.к. отчёт группирует время по задаче, а не по репозиторию.

### Три репозитория

Лидером всегда остаётся одна сессия — та, что лидирует по вниманию:

A: Active → Superseded (B обогнал) → остаётся Active(paused)
B: Pending → Active (стал лидером) → Superseded (C обогнал)
C: Pending → Pending → Active (стал лидером)

### Dynamics от rebase/merge

Rebase может генерировать большие diff dynamics (100+ строк), которые не являются
реальной разработкой. Ограничение объёма (`VOLUME_GAIN_MAX` = 6) сводит влияние
любого одиночного всплеска на stamina к нескольким тикам.

Счётчики свидетельств (коммиты / строки на сессии) по построению устойчивы к rebase:
они вычисляются каждый тик относительно *свежего* merge-base с веткой по умолчанию,
с baseline-дельтой на сессию (см. session-tracker). Squash, amend, drop и cherry-pick
их тоже не портят — коммиты накапливаются только из положительных скачков
счётчика коммитов ветки.

### Сессия в состоянии Pending

Pending-сессии накапливают score в evaluator, но не трекают время.
Они конкурируют за лидерство через EMA внимания (см. §6).

Pending-сессия переходит в Active когда становится лидером.
До этого она остаётся Pending вне зависимости от количества dynamics.

Pending-сессии закрываются при:
- Checkout на другую ветку → ClosedBy.CheckoutOtherTask
- Граница дня → ClosedBy.DayBoundary
- Никогда не стала Active → исключается из отчёта (время не трекалось)

## 12. Сводная таблица констант <a name="constants-summary"></a>

### Конфигурируемые (в config.json → session)

| Поле | По умолчанию | Описание |
|------|-------------|----------|
| `diffPollSeconds` | 30 | Интервал опроса. Алгоритм адаптируется к любому значению. |
| `idleTimeoutMinutes` | 20 | НЕ используется адаптивным алгоритмом напрямую. Оставлен для возможного simple-mode в будущем. |

### Константы алгоритма (захардкожены в constants.ts)

| Константа | Значение | Обоснование |
|-----------|----------|-------------|
| `SENSITIVITY_TIMEOUTS` | low 15 / normal 45 / patient 90 / always_on 45 мин | Единственная ручка на уровень: потолок stamina = максимальный запас |
| `STAMINA_FLOOR_RATIO` | 1/4 | Порог касания = потолок / 4 (Normal: 11.25 мин) — ни шума пауз, ни прыжка шкалы, переживает раздумье без набора |
| `EMA_WINDOW_MINUTES` | 10 | Память частоты ~15 мин, забывает после ~30 мин простоя |
| `ATTENTION_WINDOW_MINUTES` | 2 | Лидерство следует за разработчиком в пределах ~2 мин |
| `FREQUENCY_GAIN_MAX` | 2 | Устойчивый каждотиковый поток сам по себе обгоняет затухание |
| `STAMINA_LINES_PER_MINUTE` | 8 | 8 строк/мин = +1 score за тик; breakeven при 4 строках за 30с-тик |
| `VOLUME_GAIN_MAX` | 8 | Массовые вставки ограничены — наполнение шкалы требует устойчивой активности |
| `IN_PLACE_CHURN_LINES` | 8 | Строки-эквиваленты за файл, переписанный «на месте» (плоский numstat, изменившийся хеш содержимого) |
| `CHURN_MAX_FILES` | 100 | Лимит churn-скана за тик (чтения/хеширования файлов) |
| `CHURN_MAX_FILE_BYTES` | 2 МБ | Слишком большие/бинарные файлы не дают churn |
| `COMMIT_BONUS_SECONDS` | 240 | Коммит добавляет ~4 мин буфера — коммиты раз в несколько минут при подготовке ветки к ревью не должны уходить в паузу |
| `BASE_DECAY` | 1 | Затухание на активных тиках и на/ниже порога |
| `DECAY_BOOST` | 2 | Затухание при простое выше порога = 1 + 2×EMA, никогда сквозь порог — плотные кодеры остывают быстрее спорадических, но мягко (полная шкала Normal ≈ 30 мин), чтобы раздумье не читалось как перерыв |

### Контракт (TypeScript)

```typescript
interface ActivitySignals {
  readonly hasDynamics: boolean;
  readonly hasCommit: boolean;
  readonly deltaMagnitude: number;  // строки-эквиваленты per-file churn
                                    // (evidence diff + untracked + in-place, см. §5)
}

interface TickInput {
  readonly sessionId: string;
  readonly signals: ActivitySignals;
  readonly maxTicks: number;            // потолок чувствительности в тиках
  readonly ignoreIdleTimeout: boolean;  // always_on
  // Примечание: сессии на ручной паузе ВООБЩЕ не отправляются в evaluator (полная заморозка)
}

interface EvaluatorResult {
  readonly scores: Map<string, SessionScore>;
  readonly leaderId: string | null;  // лидер по вниманию (см. §6), null если все score=0
}

interface SessionScore {
  readonly score: number;
  readonly maxScore: number;         // = maxTicks
  readonly normalizedScore: number;  // score / maxScore (0..1) — шкала Stamina
  readonly ema: number;
  readonly etaTicks: number;         // тиков до авто-паузы (симуляция асимметричного угасания)
  readonly isIdleTimeout: boolean;   // score == 0
}

class ActivityEvaluator {
  constructor(diffPollSeconds: number);
  processAllTicks(ticks: readonly TickInput[]): EvaluatorResult;
  removeSession(sessionId: string): void;
}
```
