# Use Cases: Activity Evaluator

Сценарии для ручной верификации алгоритма перед разработкой.
Все примеры: `diffPollSeconds=30`, тик = 30с, чувствительность Normal:
MAX_TICKS=90 (потолок 45 мин), пол касания = MAX_TICKS/6 = 15 тиков (7.5 мин),
idle decay = 1 + 4×EMA, активный тик −1 (асимметричное угасание),
прирост частоты ≤ +2/тик, прирост объёма ≤ +4/тик, commit bonus +5 тиков,
окно EMA частоты 10 мин (α≈0.05), окно attention 2 мин (α=0.25, лидерство).

---

## UC-1: Классический рабочий день (1 репо)

```
09:00  Daemon запущен. Сессия A открыта (Pending), score=0.
09:00  Первый dynamics → score = пол 15 (бар ~17%), единственная сессия, score>0 → лидер → Active.
       startedAt = 09:00.
09:00-12:00  Непрерывная работа, dynamics каждый тик (10-15 строк).
       EMA → 1.0 за ~10 мин, прирост за тик ≈ +2 (частота) + 2-3 (объём) − 1 (decay) → +3..4.
       Бар полный (score=90) через ~20-25 мин, дальше cap.
12:00  Ушёл на обед. Последний dynamics (бар полный, EMA≈1).
12:15  score=0 (~30 тиков асимметричного затухания: 1+4×EMA ≈ 5/тик вначале,
       ослабевает по мере остывания EMA) → IdleTimeout.
       Pause { from: 12:15, source: idle_timeout }.
13:30  Вернулся, первый dynamics.
       EMA затухла до ~0 ((1-0.05)^180 ≈ 0).
       score = пол 15 (бар ~17%, поводок ~6.5 мин) > 0, единственная сессия → лидер.
       Pause closed { to: 13:30 }. Трекинг продолжается, бар отстраивается заново.
13:30-17:30  Работа с перерывами на чай (~5 мин — запаса шкалы хватает даже
       при ускоренном затухании, пауз нет).
17:30  Последний dynamics (бар ~60%, score≈54, EMA≈0.5 — работа была с перерывами).
17:42  score=0 (~25 тиков, затухание ≈ 1+4×0.5 = 3/тик вначале) → IdleTimeout.
18:00  workday stop → сессия закрыта (ClosedBy.DaemonStop).

Итого: ~8ч реального времени, минус обед (1ч 15м паузы) и хвост дня.
```

**Проверяем:** обед вычтен через IdleTimeout, причём пауза началась уже через ~15 мин после последней правки — резкая остановка после плотной работы (полный бар, EMA≈1) — самый сильный сигнал паузы. Умеренный бар вечером угас за ~10-12 мин. Чайные паузы ~5 мин не вызвали паузу.

## UC-2: Медленный code review (1 репо)

```
10:00  Checkout на ветку коллеги для ревью. Сессия A открыта (Pending).
10:00-10:40  Читает код, нет dynamics. Score=0.
       Сессия остаётся Pending. Никаких пауз (нечего паузить).
10:40  Оставил один комментарий в коде (1 строка). Dynamics.
       score = пол 15 (+ ~0.3 приростов), единственная сессия → лидер → Active. startedAt=10:40.
10:46  score затух до 0 → IdleTimeout (одно касание, EMA≈0, decay≈1 →
       поводок ~13 тиков ≈ 6.5 мин).
10:55  Ещё комментарий (dynamics). Auto-resume, pause closed. score = пол 15.
11:01  score=0 → снова IdleTimeout.
11:10  Переключился на свою ветку → checkout → ClosedBy.CheckoutOtherTask.

Итого A: startedAt=10:40, closed=11:10, из них залогировано ~13 мин
(2 касания × ~6.5 мин поводка от пола), промежутки — паузы idle_timeout.
40 минут чтения без правок НЕ залогированы (Pending).
```

**Проверяем:** Pending-период (10:00-10:40) не учтён. Редкие лёгкие правки дают только пол (поводок ~6.5 мин на касание, decay≈1 при EMA≈0) — бар не растёт. Если для этого репо чтение с редкими правками — это работа, репо стоит перевести в Patient (пол = 90/6 = 15 мин, разрывы до 15 мин покрыты).

## UC-3: Переключение между двумя репо (одна задача ATL-123)

```
09:00  Работаю в frontend (A). Active, бар полный (score=90), attention≈1.0.
10:30  Переключился на backend (B), начал API endpoint. A простаивает.

10:30:00  Тик 1: B dynamics. B score = пол 15. B att=0.25 vs A att 0.75+0.25 (маржа) → A лидер.
10:30:30  Тик 2: B att=0.44 vs A 0.56+0.25=0.81 → A всё ещё лидер.
10:31:30  Тик 4: B att=0.68 vs A 0.32+0.25=0.57 → B лидер! (~2 мин после переключения)
          B: Pending → Active, startedAt=10:32.
          A: Pause(Superseded). A score продолжает затухать (не заморожен),
          причём быстро (EMA была ≈1 → decay ≈5/тик вначале): к ~10:47 дойдёт до 0.
11:30  Вернулся в frontend (A). Dynamics в A каждый тик.
       Симметрично: A att растёт, B att затухает → A пересекает маржу за ~4 тика.
11:32  A лидер, Pause(Superseded) у A закрыта, score = пол 15 (+приросты).
       B: Pause(Superseded) → затухает → IdleTimeout.
12:00  Обед.

Итого дня:
  A: 09:00-10:32 (active), 10:32-11:32 (superseded), 11:32-12:00 (active)
  B: 10:32-11:32 (active), 11:32+ (superseded → idle_timeout)
  Задача ATL-123: A + B = ~3ч (без пересечений)
```

**Проверяем:** пересечение = 0. Передача лидерства за ~2 мин (4 тика attention EMA), независимо от заполненности баров. Время группируется по задаче корректно.

## UC-4: Стрей dynamics во время звонка (2 репо)

```
14:00  Активно работаю в A (лидер, бар полный, EMA≈1, attention≈1.0). Ушёл на звонок.
14:05  На звонке. Случайно задел клавишу в B, сохранил файл. 1 строка.
       B: score = пол 15 (бар ~17%), attention = 0.25.
       A: attention затухла (5 мин простоя), но маржа защищает:
       претенденту нужно att > A_att + 0.25, а одно касание даёт ровно 0.25 —
       превысить маржу одним касанием невозможно по построению.
       A по-прежнему лидер (score ещё > 0: полный бар после плотной
       работы = ~15 мин поводка при асимметричном затухании).
       B остаётся Pending.
14:05+  B score затухает: 15 → 0 за ~6.5 мин (EMA B ≈ 0, decay≈1).
       Сессия B закрывается как Pending к ~14:12.
14:15  A: score=0 (~30 тиков затухания после плотной работы) → IdleTimeout —
       звонок честно уходит в паузу.

Итого: стрей не повлиял на A; сам звонок распознан как пауза через ~15 мин.
B исключена из отчёта.
```

**Проверяем:** случайное касание не крадёт лидерство — маржа гистерезиса равна вкладу одного касания, кража невозможна структурно, даже если лидер давно простаивает.

## UC-5: Ручная пауза + забыл resume (1 репо)

```
12:00  Активно работаю. A: Active, score=80 (бар ~89%), EMA=0.9.
12:01  workday pause → ручная пауза. Evaluator заморожен (score=80, EMA=0.9).
12:01-13:30  Обед + митинг. Score заморожен на 80.
13:30  Забыл нажать resume. Открыл IDE, начал кодить.
13:31  Dynamics в A.
       SessionTracker: "ручная пауза, но есть активность → закрываю паузу".
       Pause { from: 12:01, to: 13:31, source: manual }.
       Evaluator размораживается: score=80, EMA=0.9.
       Тик: пол (уже выше), +1.8 (частота, min(1,0.9)×2), +объём, −1 decay → ≈81.
       Нормальная работа продолжается, бар добирается до cap 90.

Итого: 1.5ч паузы корректно записаны. Авто-resume при git-активности сработал.
```

**Проверяем:** замороженный score = естественный grace period (score 80 при размороженной EMA 0.9 → ~13 мин на раскачку при асимметричном затухании). Забытый resume не потерял время.

## UC-7: Быстрый пинг-понг frontend/backend (2 репо, одна задача)

```
10:00  Работаю в A (frontend). Active, лидер.
10:05  Переключился в B (backend). Dynamics каждый тик → attention B растёт,
       пересекает маржу за ~4 тика (~2 мин) → 10:07 B лидер.
       A: Superseded. B: Active.
10:10  Вернулся в A. Dynamics каждый тик → ~10:12 A лидер. B: Superseded.
10:15  Снова в B. ~10:17 B лидер. A: Superseded.
10:20  Обратно в A. ~10:22 A лидер.

За 20 минут: 4 переключения, каждая передача лидерства занимает ~2 мин
(гистерезис attention EMA — защита от дёрганья на одиночных тиках).
Каждое переключение создаёт/закрывает Superseded паузу.
Задача ATL-123: суммарное время из A + B = 20 мин (корректно —
границы сдвинуты на лаг передачи, но сумма непрерывна).
```

**Проверяем:** частые переключения корректно обрабатываются, лаг передачи ~2 мин не теряет время по задаче. Отчёт по задаче суммирует обе сессии.

## UC-11: Лёгкий кодер vs тяжёлый конкурент (2 репо)

```
09:00  Работаю в A лениво (1 dynamics / 15 мин).
       EMA≈0.05, каждое касание: score = пол 15 → затухает до 0 за ~6.5 мин →
       IdleTimeout → auto-resume на следующем касании. Бар никогда не растёт выше пола.
       Attention A: всплеск 0.25 на касании, затухает почти до 0 за ~2 мин.
09:50  Переключился в B, начал интенсивно кодить (каждый тик).
       Тик 1: B att=0.25 vs A att≈0.04+0.25 (маржа) ≈ 0.29 → A ещё лидер.
       Тик 2: B att=0.44 vs ≈0.28 → B лидер! (~1 мин: слабый защитник — быстрая передача)
       A: Superseded (если score>0) либо уже IdleTimeout.
       B: Pending → Active. Бар B растёт: +3..4/тик, через 20 мин ≈ 60-70%.
10:15  B: перестал кодить. Score B затухает от ~70 (не заморожен),
       причём быстро: EMA B ≈ 1 → idle decay ≈ 5/тик вначале.
10:20  Вернулся в A. Dynamics.
       Тик 1: A att=0.25 vs B att≈0.06+0.25=0.31 → не хватает!
       (одно касание никогда не отбирает лидерство — даже у простаивающего лидера)
       Тик 2: ещё dynamics → A att=0.44 > 0.31 → A лидер (~1 мин).
       B: Superseded → score затухает → IdleTimeout к ~10:25
       (плотный кодер остывает за ~10-15 мин, а не за 45).

Итого: лидерство решает attention EMA, а не заполненность баров.
Лёгкий кодер возвращает лидерство за 2 активных тика, но на Normal
его 15-минутные паузы между правками честно уходят в idle_timeout.
```

**Проверяем:** одиночное касание не может ни украсть, ни вернуть лидерство (маржа = вклад одного касания); устойчивая активность забирает лидерство за ~1-2 мин независимо от того, чей бар полнее. Для «лёгкого» стиля работы без пауз нужен Patient (пол 15 мин).

## UC-14: Два репо, оба Pending, кто станет Active?

```
09:00  Daemon запущен. A открыта (Pending), B открыта (Pending).
       Обе score=0. Нет лидера (leaderId=null).
09:05  Dynamics одновременно: в A 5 строк, в B 10 строк.
       processAllTicks() обрабатывает обе за один вызов.
       A: пол 15 + 0.1 (частота, EMA=0.05) + 1.0 (объём 5/5) − 1 = 15.1, бар ~17%.
       B: пол 15 + 0.1 + 2.0 (объём 10/5) − 1 = 16.1, бар ~18%.
       Attention: у обеих по 0.25 (первое касание), защитника-лидера нет →
       побеждает высшая attention, при равенстве — tiebreak по normalizedScore.
       B(0.179) > A(0.168) → B лидер → Active. A остаётся Pending.

Итого: при одновременном первом dynamics и равной attention побеждает
тот, у кого выше normalizedScore — объёмный прирост решает.
```

**Проверяем:** конкуренция Pending-сессий работает корректно. Первый лидер определяется за один тик, tiebreak — normalizedScore.

## UC-15: autopause off + переключение на другой репо

```
10:00  A: Active, лидер. workday autopause off (для A).
10:00-11:00  Читает код в A, нет dynamics. Score=0, attention≈0,
       но IdleTimeout подавлен — A остаётся лидером и трекает время.
11:00  Начал кодить в B. Dynamics каждый тик.
       Тик 1: B att=0.25 vs A att 0+0.25 (маржа) → не хватает.
       Тик 2: B att=0.44 > 0.25 → B лидер (~1 мин: A давно без attention).
       A: Superseded (autopause off не защищает от Superseded).
       B: Pending → Active.

11:30  Вернулся в A. Dynamics каждый тик (B простаивает).
       Тик 1: A att=0.25 vs B 0.75+0.25=1.0 → B ещё лидер.
       Тик 4: A att=0.68 vs B 0.32+0.25=0.57 → A лидер (~2 мин).
       A: Superseded закрыта (resume), score = пол 15, бар отстраивается.
       B: Superseded.

Итого: autopause off не даёт бесконечное лидерство — Superseded всё равно работает.
       Это правильно: нельзя быть лидером двух репо одновременно.
```

**Проверяем:** autopause off подавляет IdleTimeout, но НЕ Superseded. Передача лидерства идёт через attention EMA с гистерезисом. Защита от «забыл включить обратно».
