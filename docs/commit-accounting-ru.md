# Учёт коммитов и строк — Commit Ledger

Цель: счётчики каждой сессии *точно* отвечают на два вопроса:

- **commits** — сколько коммитов по итогу породила эта сессия. Сквош двух
  сессионных коммитов уменьшает счётчик 2 → 1. Сквош сессионного коммита
  *в* до-сессионный счётчик **не** уменьшает — работа сессии выжила внутри
  переписанного коммита. Удалённые (`reset --hard`, drop) коммиты перестают
  считаться; коммиты, влитые в default-ветку, продолжают считаться.
- **lines** — сколько строк составляет работа сессии прямо сейчас (тоталы
  ветки против merge-base минус всё, что на ветке было на момент открытия
  сессии).

Счётчики **строго ограничены рамками сессии**. Сессия открывается с нуля,
её счётчики замораживаются в момент закрытия, и ничего сделанное вне сессии
— демон остановлен, сессия закрыта, работа на другой ветке — не учитывается
никогда. После рестарта демона новая сессия начинается с нуля.

## Почему опрос счётчиков не может быть точным

Демон опрашивает раз в 30 секунд. Между двумя опросами может произойти
сколько угодно git-операций: `commit` + `reset --soft` + `commit` (сквош)
виден как чистый скачок счётчика на 0 или +1, и восстановить произошедшее
из двух сэмплов `rev-list --count` невозможно в принципе.

## Решение: воспроизведение branch reflog

У git уже есть полный, персистентный журнал всех перемещений ветки —
**reflog ветки**. Каждый commit, amend, rebase finish, reset и merge пишет
ровно одну запись `old-sha → new-sha`, и записи не склеиваются, как бы
быстро ни шли операции. Демон хранит указатель (sha + время последней
обработанной записи) на сессию и на каждом тике воспроизводит записи выше
указателя как отдельные переходы. Поэтому пока сессия открыта, ни одна
операция между опросами не теряется — сколько бы их ни уместилось в 30
секунд.

Для каждого перехода коллектор вычисляет (относительно default-ветки,
поэтому чужие апстрим-коммиты в расчёт не попадают):

- `removed` — коммиты, достижимые из старого tip, но не из нового и не из
  default-ветки. Последнее условие важно: **свои коммиты, влитые в
  апстрим, никогда не считаются удалёнными** — влитая работа выживает.
- `added` — коммиты, достижимые из нового tip, но не из старого и не из
  default-ветки, с полными метаданными (tree, email/дата автора, дата
  коммиттера).

## Леджер

Сессия несёт леджер: множество идентичностей коммитов, виденных на ветке,
каждый с флагами `live` (ещё существует) и `sessionCreated` (порождён этой
сессией — напрямую или через переписывания). `evidence.commits` = live ∧
sessionCreated.

Добавленный коммит классифицируется каскадом сопоставления с ушедшими,
ещё не поглощёнными записями леджера:

1. **Известный SHA** → воскрешение (reset назад на старый tip).
2. **Совпадение tree** → сквош: tree нового коммита равен tree удалённого,
   значит он поглощает всю цепочку, удалённую тем же переходом, и
   наследует `sessionCreated` как OR по цепочке. Именно это правило
   сохраняет счётчик при сквоше сессионного коммита в до-сессионный
   (`rebase -i` оставляет author-дату старого коммита, правду видит только
   tree).
3. **Совпадение автора** (email + author timestamp) → rebase pick / amend /
   reword: git сохраняет author timestamp через эти операции, и переписанный
   коммит наследует принадлежность оригинала. Ребейз до-сессионных коммитов
   их *не* пересчитывает.
4. **Нет совпадения** → действительно новый; считается, если его committer
   timestamp позже открытия сессии (минус люфт в два тика, чтобы коммит,
   который сам открыл сессию, был учтён) И его SHA ещё не записан в леджере
   более ранней сессии за день (коммит, сделанный за секунды до
   закрытия/переоткрытия, попадает в люфт следующей сессии — проверка по
   множеству SHA не даёт пересчитать его повторно). Merge-коммиты не
   считаются никогда.

### Посев (seeding)

При открытии сессии леджер засевается всеми коммитами между merge-base и
HEAD — все помечаются как до-сессионные, счётчик стартует с нуля. Базлайн
строк снимается с тоталов ветки на первом тике: строки, которые ветка уже
несла (включая незакоммиченную работу, сделанную до сессии), исключены.

### Лестница деградации

- Указатель выпал из окна reflog (очень долгий простой) → **resync**: флаги
  live перестраиваются по текущему состоянию ветки; коммиты, исчезнувшие с
  ветки, но достижимые из default-ветки, продолжают считаться (влиты).
- Reflog ветки недоступен (`core.logAllRefUpdates` выключен) или не
  резолвится default-ветка/merge-base → работает старый счётчик
  **положительных скачков** (не видит сквоши, но не теряет насчитанное).

## Известные ограничения

- Счётчики сессий не аддитивны при переписывании истории *между* сессиями:
  сквош коммитов закрытой сессии в более поздней не уменьшает задним числом
  её замороженный счётчик (каждое число честно для своего окна, но сумма
  может отличаться от того, что в итоге выжило на ветке).
- Тоталы строк привязаны к состоянию ветки: при вливании ветки в
  default-ветку посреди сессии тоталы схлопываются и счётчики строк идут с
  новой базы (счётчик коммитов не страдает — влитые коммиты продолжают
  считаться).
- Сквош с дополнительными staged-правками (tree не совпадает ни с одним
  удалённым коммитом) уходит в правило 4: результат считается одним новым
  сессионным коммитом — итоговое число всё равно верно, если сквошилась
  сессионная цепочка.
- `git reflog expire` или отключение reflog убирает журнал — леджер
  деградирует по лестнице выше.
